# Service Desk Lite

Минимальная рабочая версия учебной системы внутренних заявок. Интерфейс — Next.js 16, управляемая авторизация — Auth0, данные и Row Level Security — PostgreSQL/Supabase, целевой хостинг — Vercel.

Приложение использует только вымышленные учебные записи. Файловые вложения в этой версии отсутствуют.

## Что реализовано

- три роли: пользователь, специалист и администратор;
- личные заявки пользователя и прямой запрет доступа к чужим ID;
- очереди специалиста по явно назначенным категориям;
- создание заявки, комментарии, назначение на себя и допустимые переходы статусов;
- управление пользователями, ролями, категориями, SLA и очередями специалиста;
- SLA по часовому поясу, рабочим интервалам и календарным исключениям;
- аудит входов, смены ролей и административных изменений без текста заявок;
- Auth0-сессия, CSRF-токены, серверная Zod-валидация, rate limit, CSP и безопасные заголовки;
- RLS и серверные RPC с правилом «запрещено по умолчанию».

## Модель доступа

| Операция | Пользователь | Специалист | Администратор |
|---|---|---|---|
| Читать заявку | Только свою | Только разрешённые категории | Любую |
| Создать заявку | Да | Нет | Нет |
| Изменить новую неназначенную заявку | Только свою | Нет | Нет |
| Комментировать | Свою, публично | Разрешённую категорию, публично/внутренне | Нет |
| Взять в работу / изменить статус | Нет, кроме подтверждения или возврата решения | Только назначенную себе заявку разрешённой категории | Нет |
| Роли, пользователи, категории, очереди, аудит | Нет | Нет | Да |

Проверка выполняется на маршруте, в серверном слое доступа и политиками/RPC базы. Клиентское меню не считается средством авторизации.

## Требования

- Node.js `>=22.13.0`;
- проект Auth0 с Database Connection;
- проект Supabase/PostgreSQL;
- Supabase CLI для применения миграций (либо SQL Editor в учебной среде).

## 1. Настройка Auth0

1. Создайте **Regular Web Application**.
2. Для локальной разработки добавьте:
   - Allowed Callback URL: `http://localhost:3000/auth/callback`;
   - Allowed Logout URL: `http://localhost:3000`;
   - Allowed Web Origin: `http://localhost:3000`.
3. В production замените origin на точный HTTPS-домен Vercel. Preview-домены добавляйте только при необходимости.
4. Используйте Database Connection и отключите самостоятельную регистрацию: аккаунты создаёт только администратор приложения.
5. Включите Brute-force Protection и Breached Password Detection. Rate limit фактической проверки пароля должен оставаться на Auth0; дополнительное правило Vercel WAF можно применить к `/auth/login`.
6. Настройте интеграцию Auth0 в Supabase и добавьте в ID token верхнеуровневый claim `role` со значением `authenticated`, как требует интеграция Supabase Third-Party Auth. Используйте асимметричную подпись JWT.
7. Создайте отдельное Auth0 Machine-to-Machine Application для Management API и выдайте только `create:users` и `delete:users`. Эти credentials используются сервером для приглашений.

SDK предоставляет маршруты `/auth/login`, `/auth/callback` и `/auth/logout`. Пароли приложение не принимает, не хранит и не журналирует.

## 2. Настройка Supabase и миграций

Добавьте Auth0 как Third-Party Auth provider в Supabase, затем примените миграцию:

```bash
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase db push
```

Миграция находится в `supabase/migrations/20260807150000_service_desk_initial.sql`. Она создаёт `profiles`, `tickets`, `comments`, `categories`, `audit_events`, назначения категорий, историю заявки, рабочие календари и внутренний rate limit.

В миграции есть только обезличенные категории и расписание `Europe/Moscow`, понедельник–пятница, 09:00–18:00. Праздничные исключения намеренно не заполнены: администратор БД должен добавить актуальный согласованный календарь до production.

### Первый администратор

Первый аккаунт создаётся вручную в Auth0, после чего его `sub` связывается с профилем. Используйте собственный учебный адрес; значения ниже — несуществующий пример:

```sql
insert into public.profiles (auth_subject, display_name, email, role, state)
values ('auth0|REPLACE_WITH_SUB', 'Администратор учебной среды', 'admin@example.test', 'admin', 'active');
```

Все следующие аккаунты приглашает этот администратор через интерфейс.

## 3. Переменные окружения

Скопируйте шаблон и заполните его локально:

```powershell
Copy-Item .env.example .env.local
```

| Переменная | Назначение |
|---|---|
| `AUTH0_DOMAIN`, `AUTH0_CLIENT_ID`, `AUTH0_CLIENT_SECRET` | Regular Web Application Auth0 |
| `AUTH0_SECRET` | Случайный секрет cookie не короче 32 символов |
| `APP_BASE_URL` | Точный origin приложения |
| `AUTH0_MGMT_CLIENT_ID`, `AUTH0_MGMT_CLIENT_SECRET` | Ограниченное M2M-приложение |
| `AUTH0_CONNECTION` | Имя Database Connection |
| `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` | URL и publishable key проекта |
| `SUPABASE_SERVICE_ROLE_KEY` | Только серверное создание профилей |
| `CSRF_SECRET` | Отдельный случайный секрет не короче 32 символов |

Ни одна секретная переменная не имеет префикса `NEXT_PUBLIC_`. Не сохраняйте `.env.local` в Git и не копируйте service-role key в браузерные настройки.

## 4. Локальный запуск

```bash
npm install
npm run dev
```

Откройте `http://localhost:3000`. Без полного набора env приложение показывает безопасный экран настройки и не пытается подключаться к провайдерам.

## Учебные аккаунты

После bootstrap администратора создайте через экран «Пользователи» три отдельных аккаунта. Адреса ниже — документационные placeholder-значения и не получают почту:

| Роль | Пример | Подготовка |
|---|---|---|
| Пользователь | `learner.user@example.test` | Создать две заявки |
| Специалист | `learner.specialist@example.test` | Назначить только категорию «Приложения» |
| Администратор | `learner.admin@example.test` | Не использовать для обычной работы |

Фиксированных тестовых паролей нет. Пользователь задаёт пароль только на стороне Auth0 по письму сброса/приглашения. Для работающих тестов используйте контролируемые адреса учебного домена и не вводите реальные конфиденциальные данные.

## Проверки

```bash
npm run lint
npm run typecheck
npm test
npm run security:check
npm run build
```

Тесты доказывают default deny для анонимного субъекта, владение заявкой, границы очереди специалиста, admin-only операции, отклонение некорректного ввода, CSRF-привязку и отсутствие серверных секретов в клиентских модулях.

После `supabase db reset` запустите транзакционные pgTAP-тесты настоящих политик:

```bash
supabase test db
```

Файл `supabase/tests/access_control.sql` использует только адреса `.test` и откатывает все fixtures. Проверку с настоящими Auth0 JWT выполняйте дополнительно в отдельном тестовом Supabase-проекте.

## Vercel (не выполнять без отдельного подтверждения)

1. Импортируйте репозиторий как Next.js-проект.
2. Добавьте все переменные из `.env.example` отдельно для нужных окружений. Секреты задавайте только как server-side Environment Variables, без `NEXT_PUBLIC_`.
3. Задайте `APP_BASE_URL` точным HTTPS-origin и обновите Auth0 callback/logout/origin allowlists.
4. Для endpoint `/auth/login` включите ограничение Vercel WAF, а в Auth0 оставьте защиту от перебора для фактического ввода пароля.
5. Сначала выполните миграцию в отдельном preview/staging Supabase-проекте, затем smoke-тест ролей. Production migration запускайте отдельным контролируемым шагом.

Этот репозиторий не публикует и не деплоит приложение автоматически.

## Резервное копирование

- включите доступные для выбранного плана Supabase ежедневные backups или Point-in-Time Recovery;
- перед миграцией делайте логический backup схемы и данных из доверенной CI/административной среды;
- шифруйте архивы, ограничивайте срок хранения и не помещайте ключи в имя или лог backup-задачи;
- регулярно проверяйте восстановление в отдельный проект, включая RLS и функции;
- Auth0 identities резервируются и восстанавливаются средствами Auth0; база приложения хранит только связь по `sub`, а не пароли.

## Известные ограничения

- файлов и вложений нет;
- нет уведомлений о заявках и фоновой эскалации SLA;
- праздничный календарь требует наполнения;
- история в интерфейсе пока показывает краткое состояние; полный журнал событий хранится сервером;
- блокировка профиля и деактивация категории пока выполняются административно в БД;
- интеграционные RLS-тесты требуют отдельного Supabase-проекта и тестовых Auth0 JWT;
- login rate limit зависит от настроек Auth0 и, при использовании, Vercel WAF;
- backup/PITR, WAF и preview-изоляция зависят от выбранного тарифа и конфигурации провайдеров.
